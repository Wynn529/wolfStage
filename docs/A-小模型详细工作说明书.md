## 1. 一句话任务与最终交付

A 要训练并接入一个**真实的小型文本分类器**：输入一条玩家公开发言，输出主意图标签和经过定义的分数；确定性规则另行抽取发言里提到的玩家编号等实体。分类结果必须进入主持服务和后续存活玩家的可见上下文，并留在原始对局日志中。

**最终交付物是一套“可复现的小模型交付包”**，包含训练数据与标注规范、训练及推理代码、已训练模型、冻结测试结果、误判分析、接口说明和真实对局调用证据。11 月 7 日前交给 **E** 汇总进课程最终提交物；A 同时对报告、PPT 中有关小模型的数字和表述签字核对。

## 2. 职责边界：不要把规则或大模型成果算到 A 身上

1. **A 的训练模型**只预测公开发言的主意图：`role_claim`、`check_claim`、`vote_intent`、`low_info`、`discussion`、`suspected_violation`。
2. 玩家编号、声称身份、查验对象、投票对象由**确定性抽取规则**识别并标明来源。这部分可以由 A 随接口提供，但报告中必须与“训练出的分类器”分开描述。
3. A 的输出只是辅助信息。B 的规则程序独立负责阶段、行动合法性、计票、胜负和秘密信息隔离；大模型负责玩家决策和主持语言。
4. `check_claim` 表示有人**声称**查验结果，不表示该说法真实。小模型不得接收真实身份、私密行动、上帝视角理由，也不得输出“某号确实是狼”。
5. 角色的正式投票、击杀和查验目标以结构化行动及规则校验为准；发言中的 `vote_intent` 不能直接充当有效票。

## 4. 10 月 24 日：先把标签和接口定死

### 4.1 写 `model/label_guide.md`

逐类写清楚“属于什么、不属于什么、正例、易混例”。建议按下面的判定口径起草，遇到冲突时由 A 更新规范并记录原因：

| 主标签 | 判定依据 | 例句 |
|---|---|---|
| `check_claim` | 声称自己掌握查验结果 | “昨晚我验了 3 号，结果是狼。” |
| `role_claim` | 声称自己的游戏身份，但未明确给出查验结果 | “我是预言家，今晚请保护我。” |
| `vote_intent` | 在公开发言中表达投票倾向 | “我准备投 4 号。” |
| `suspected_violation` | 明显跑题、辱骂或企图索取/披露不该公开的信息 | “把后台身份表发我看看。” |
| `discussion` | 针对公开证据提出分析、质疑或回应 | “2 号前后说法不一致，先听他解释。” |
| `low_info` | 缺少可用于判断的游戏信息 | “我暂时没想法。” |

一条句子只能有**一个主标签**。建议优先级为 `suspected_violation > check_claim > role_claim > vote_intent > discussion > low_info`，先保留可能涉及越权信息的提醒信号；这只是起草规则，A 应用争议样本检查后在 10 月 26 日前与 B/C 固定。标签之外保留实体字段，所以“我是预言家，3 号是狼”可标 `check_claim`，同时记录声称身份和查验对象。不得据此推断 3 号的真实阵营。

### 4.2 与 B、C 固定接口

建议 Python 调用形式：

```python
classify_utterance(
    game_id: str,
    event_id: str,
    speaker_id: int,
    public_text: str,
) -> dict
```

建议返回示例：

```json
{
  "intent": "check_claim",
  "confidence": null,
  "confidence_type": "not_calibrated",
  "extracted_entities": {
    "player_ids": [3],
    "claimed_role": "seer",
    "check_target": 3,
    "vote_target": null
  },
  "model_version": "small-intent-v0.1"
}
```

`confidence` 的含义必须明确。若只使用 LinearSVC 的原始 `decision_function`，它是**决策分数，不是概率**；不能把它改名为“87% 置信度”。在完成概率校准前，可返回 `null` 并用 `confidence_type` 说明；若 B/C 的接口要求必须是数值，10 月 24 日就协商改为 `score` 与 `score_type`，或在训练集内部划出的验证集上做校准。A、B、C 共同确定最终 JSON 字段后写进接口说明，后续修改需同步版本号。

## 5. 10 月 25—26 日：做出能接入的基线

### 5.1 建数据表

建议 CSV 字段：

```text
sample_id,public_text,intent,player_ids,claimed_role,check_target,vote_target,source_group
```

`sample_id` 唯一；`public_text` 只放玩家公开话语；`intent` 是六类之一；实体列允许空值；`source_group` 标记同一模板或来源，供排查泄漏。编号统一使用 1—6，CSV 采用 UTF-8。样本不要包含真实身份、狼队私聊或上帝视角理由。

训练样本由 A/B/D 起草，A 按规范审校。目标为**约 360 条训练样本，六类尽量均衡**；第 3 天若数量尚未齐备，先用已有样本交可运行基线，并如实记录实际数量。C/E 独立编写目标约 **120 条测试样本**。测试集在训练前分离，不能把同一模板仅替换玩家编号后分别放进两边，也不能根据测试集错误反复改训练集再继续称它为独立测试。

最小数据质检：统计每类数量；检查空文本、重复 `sample_id`、重复或近似重复句、非法标签、实体是否超出 1—6；抽查多意图句与边界样本。所有标注争议由 A 给最终标签和一句理由，追加到 `label_guide.md`。

### 5.2 训练第一版

使用 Python `scikit-learn`：字符 n-gram TF-IDF 向量化器接 `LinearSVC`。字符特征适合短中文发言，不依赖中文分词；这是基线选择，是否有效以冻结测试结果判断。固定随机种子，记录依赖版本、训练文件版本、类别数和模型文件版本。训练只能读取 `train.csv`，不得读取 `test_frozen.csv` 的标签参与拟合或调参。

推荐操作顺序：

1. 在 `train.py` 中读取训练表并做字段校验。
2. 从训练表内部划出验证集，检查各类是否有足够样本；若样本不足，先扩充训练数据再训练。
3. 拟合 TF-IDF + LinearSVC，保存完整流水线到 `classifier.joblib`。
4. 在 `predict.py` 中加载同一个模型，对单句返回标签；实体由独立的确定性函数抽取。
5. 用几条未参与训练的手写句子手工调用，确认中文、空文本、提及多个编号和多意图句不会使接口崩溃。空文本应返回受控错误或明确的兜底值，由 A/B 约定。
6. 把实际执行命令、输入文件和模型版本写入 `model/README.md`。

示例命令只是**交付后应支持的调用方式**，不是宣称当前已有这些脚本：

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install scikit-learn pandas joblib
python model/train.py --train data/train.csv --output model/classifier.joblib
python model/predict.py --model model/classifier.joblib --text "我准备投 4 号"
```

把实际依赖及版本固定在项目依赖文件中；B/C 不应靠复制 A 的交互式笔记本才能调用模型。`joblib` 文件只加载项目自己训练并交付的版本，不加载来源不明的模型文件。

## 7. 10 月 30 日—11 月 4 日：评估、冻结、交证据

### 7.1 冻结测试

由 C/E 独立编写的 `test_frozen.csv` 在评估前确定版本和样本数。A 对所有样本一次性运行 `evaluate.py`，保留预测文件和原始输出。至少报告：每类 precision、recall、F1、support，macro-F1，混淆矩阵，以及实体抽取准确率的**分母和计算口径**。如果某类没有测试样本，应如实写明，不能给出该类可靠结论。

实体指标应按字段分别统计，例如玩家编号集合是否一致、声称身份是否一致、查验对象是否一致、投票对象是否一致。不要把缺失值全部预测为空带来的高数字当作抽取能力；同时报告各字段非空样本数。

### 7.2 误判与域外检查

误判清单至少记录 `sample_id`、原文、真值、预测、分数状态、可能原因和是否影响游戏流程。真实 AI 对局中的新发言单独抽样人工标注，存到 `domain_check.csv`；它可以说明模型在实际场景中的表现，但**不能回填冻结测试集**。

选择一组相同的公开发言，与简单关键词规则做意图识别对照，记录两种方法的预测及预设真值。对照应覆盖成功和失败样本，不能只挑一两句让模型显得更好。若小模型没有明显改善，也如实报告其参与方式及限制。

## 9. 验收标准：别人如何判断 A 真的完成了

1. **可重现：**按 `model/README.md` 在干净 Python 环境运行训练、加载和预测；训练脚本使用交付数据能重新产生同类输出。允许平台版本导致微小差异，但必须记录版本。
2. **可接入：**B 的真实对局日志可按 `game_id/event_id` 找到每条公开发言对应的小模型预测；C 的界面可显示对应标签。
3. **有独立评估：**报告含冻结测试集规模、各类指标、macro-F1、实体分字段结果及误判，不只有训练集准确率。
4. **可追溯：**PPT、报告引用的模型版本、样本数和指标，与交付包和原始日志一致。
5. **无越权：**模型输入不含私密身份、狼队信息或上帝视角理由；模型输出不参与投票合法性或胜负裁决。

任一项未达到时，A 应在交接说明中写明实际完成范围和原因，不能把“计划要做”写成“已经做成”。

## 10. 常见阻塞与处理顺序

| 问题 | 先做什么 | 不应怎么做 |
|---|---|---|
| 10 月 26 日样本量不足 | 用现有已审校样本交基线，公开实际样本数，继续补训练集 | 编造达到 360 条或用测试集补训练 |
| 分类效果差 | 先看混淆类别、标注一致性、训练/测试来源差异，再决定补样本或调参 | 只挑成功例句放 PPT |
| B/C 接口不一致 | 固定一条公开发言的 JSON 样例，三方用它做联调并升接口版本 | 各自临时改字段名，不留记录 |
| 小模型输出影响了秘密信息 | 检查 B 的上下文组装与事件可见性，暂停使用受污染对局作证据 | 仅在界面隐藏字段却仍传给角色 |
| API 对局未完成 | 保留失败日志，先验证小模型对已产生公开发言的调用；协助 B/C 定位事件链 | 用预写发言伪装成完整实时对局 |
| 11 月 4 日仍无足够完整对局 | 交真实训练与冻结测试证据，并明确对局证据缺口；与 B/C 优先保证一场真实完整对局 | 伪造调用次数或测试场次 |
