## 2. B 的责任边界与工作顺序

B 负责四件事：**游戏规则与状态机、六个角色及主持的大模型调用、对外服务接口、原始日志和调用统计**。A 负责小模型训练及推理接口；C 负责界面和对局测试；D 负责 PPT/视频；E 负责报告与主讲。B 要给其他人稳定接口和可追溯证据，不能等全部功能完成后才交接。

按以下依赖顺序实施：

1. 先把 `rules.md` 和事件协议固定，使用确定性假代理跑通规则。
2. 再接 DeepSeek 适配器，使真实角色行动进入同一事件流。
3. 接 A 的 `classify_utterance`，确认结果进入主持服务和**之后行动的存活角色**的公开上下文。
4. 最后完善主持语言、成本控制、断点续跑和统计。界面美化不由 B 承担。

这样排是为了先验证“裁决正确且秘密不泄露”，再验证模型表现；否则真实 API 的随机输出会掩盖规则错误。

## 4. 10 月 24 日：把规则、信息边界和接口写清

### 4.1 写 `rules.md`，当日与 A/C 确认

只实现固定板子：1—6 号，2 狼人、1 预言家、3 平民；随机种子分配身份；首轮夜晚。两狼互知，不得击杀队友；两狼各提击杀目标，不一致时私密协商一轮，再不一致则由固定种子在有效提案中裁决并标记“规则裁决”。预言家每夜查验一名存活的其他玩家；同夜死亡仍能完成查验。天亮公布死亡者但不公布身份；存活者依编号发言一次，再各投其他存活者一票。最高票放逐；平票者重投一次，仍平票则无人放逐。狼人全灭好人胜；存活狼人数不少于存活非狼人数狼人胜。每次夜间死亡及放逐后检查胜负；最多 8 个昼夜，超限记未完成。

同时写清无效行动的处理：非法目标、死者行动、越阶段行动、重复事件不改变游戏状态；无效票留日志但不计有效票。对于“没有有效票”等边界，B 在 `rules.md` 明确按无人放逐处理，并给出用例，避免运行时临时决定。规则版本冻结后，每次改动都要同步用例预期和给 E 的说明。

### 4.2 画出每类数据的可见范围

| 数据 | 主持服务 | 对应玩家 | 其他玩家 | C 的上帝视角 |
|---|---|---|---|---|
| 真实身份、存活状态 | 全部 | 本人身份；狼人另知队友 | 不可见 | 可见 |
| 公开发言、小模型公开标签 | 可见 | 存活玩家可见 | 存活玩家可见 | 可见 |
| 狼队提案与协商 | 可见 | 两狼可见 | 不可见 | 可见 |
| 预言家查验与结果 | 可见 | 预言家可见 | 不可见 | 可见 |
| `reason` 自述理由 | 可见 | 本人可见 | 不可见 | 可见 |
| 票数、胜负 | 服务裁决 | 按阶段公开 | 按阶段公开 | 可见 |

**上帝视角是只读展示，不是角色输入源。** 给每次模型调用记录 `input_visibility` 和可见事件 ID。B 在组装 Prompt 时从带可见性标记的原始事件中筛选，不能把 C 返回的整页上帝视角状态重新塞给玩家。

### 4.3 与 C 固定 API 和事件结构

第 3 天前至少固定六个接口：`create_game(seed, role_config)`、`advance_one_event(game_id)`、`pause/resume(game_id)`、`get_events(game_id, after_event_id)`、`get_metrics(game_id)`。建议把暂停与继续实现为两个明确路由，但对 C 保持同一约定。返回值最少带 `game_id`、连续的 `event_id`、`phase`、`status`、时间、事件类型、展示字段和可见性。`advance_one_event` 必须幂等：同一待处理事件重试不能产生两个死亡、两张票或两次阶段推进。

给 C 一份最小 JSON 样例，包括公开发言、私密行动、规则裁决、小模型标签、模型调用失败各一条。上帝视角接口可以返回私密展示字段，但需要单独约定只在本地演示环境使用，不向玩家代理暴露。回放只读 `events.jsonl`，绝不重新请求模型，并显示“回放”。

## 5. 10 月 25—26 日：交可调用基线

### 5.1 先用假代理打通状态机

假代理只用于开发测试，返回合法的结构化动作；其事件必须标记 `source=stub`，不能进入“全部玩家由 API 实时生成”的演示证据。依次检查：创建对局、分配角色、两狼提案及协商、预言家查验、夜间结算、白天发言、投票、平票重投、胜负结束、8 昼夜上限。每推进一步先落事件，再返回给 C；日志保留随机种子和规则版本。

### 5.2 规定角色返回协议

角色行动采用固定 JSON，例如：

```json
{"action":"vote","target":3,"text":"我投 3 号","reason":"3 号公开发言前后不一致"}
```

`action` 只可为当前阶段允许的 `kill`、`inspect`、`speak`、`vote`；`target` 必须是允许的存活玩家编号，纯发言时可为 `null`；`text` 是公开发言或行动描述；`reason` 是简短的角色自述依据，只给上帝视角和本人，不能传给其他玩家。狼队协商另设明确的阶段/动作类型，不要把协商话语当白天公开发言。B 应为每阶段列出必填字段、长度上限及合法值。

本地解析时检查 JSON、类型、阶段、目标、可见性和文本长度。无效输出最多重试一次；再次失败则暂停该局并记录具体错误，不能偷偷改成预写行动。主持词校验失败可用固定模板播报，但必须记录 `fallback=true`。

### 5.3 10 月 26 日现场交接

在 C 的环境中按 README 启动服务，调用 `create_game` 得到 `game_id`，再调用 `advance_one_event`，由 C 用 `get_events` 显示事件。B 同步交角色 JSON 样例、错误码/状态约定、规则版本、真实 API 与 `stub` 的区分。A 确认公开发言形成后应调用其接口的位置和字段。即使真实 DeepSeek 尚未稳定，当天也必须交**真实可调用的游戏服务基线**，并明确哪些事件仍由假代理产生。

## 6. 10 月 27—29 日：接真实 API，跑通第一场

### 6.1 配置 DeepSeek 适配器

所有角色和主持通过一个适配器调用，使用各自版本化提示词、`agent_id`、私有记忆及可见历史。API Key 只从环境变量读取；日志、截图、PPT 和 Git 中不出现真实值。以实际调用前官方文档核对模型名、JSON 参数、token 字段和价格，不把单价写死。保存模型名、版本或日期、Prompt 版本、请求参数和每次 `usage`。

四套 Prompt 分别为狼人、预言家、平民、主持。共同约束为：只利用给定可见信息；返回协议 JSON；不得自行宣布票数、真实身份和胜负；`reason` 只写简短决策依据。主持输入只包含当前允许播报的规则事实，不能要求它自行裁决。首夜没有公开证据，允许角色承认不确定性；不要强制预言家幸存或狼人必定刀中预言家。

### 6.2 接 A 的小模型

每产生一条白天公开发言，B 用 `game_id, event_id, speaker_id, public_text` 调一次 `classify_utterance`，把原文、主意图、实体和模型版本写到关联事件。标签是“玩家声称/意图预测”，不是真相；`vote_intent` 不等于有效票。小模型输出进入主持服务和**后续行动**的存活角色公开上下文。若 A 返回未校准分数，按 A 的字段原样传递，不显示成概率。A 接口失败时保存失败记录并暂停或以明确的降级状态继续测试；降级对局不得作为“大小模型均参与”的证明。

### 6.3 跑一场真实对局并定位失败

固定一个随机种子，一键连续调用事件推进直到出现胜负、明确的失败或 8 昼夜上限。记录 `game_id`、角色行动顺序、各 Prompt 版本、A 模型版本、每次调用、胜方或失败事件。和 C 核对页面所见与日志一致。若 10 月 29 日仍未结束，先排查事件游标、角色可见性、JSON 校验和 API 超时；暂停界面美化与 Prompt 花样。不得用假代理或预写行动补齐演示剧情。

## 7. 10 月 30 日—11 月 1 日：补规则测试、稳定服务并冻结功能

1. 按 `tests/cases.md` 做**至少 30 个规则与异常用例**，每例列输入状态、行动、预期状态/票数/胜负、实际结果。重点覆盖两狼同意/分歧/再分歧、非法击杀、预言家同夜死亡、死者发言或投票、重复请求、空票、平票与重投、双方不同胜利条件、8 昼夜超限。
2. 做可见性测试：给狼、预言家、平民分别构造含私密事件的同一局面，检查实际送入 API 的上下文。不能仅检查前端是否隐藏。检查某个玩家的 `reason` 不出现在其他代理输入中。
3. 做一次中断恢复：在 API 调用前后分别模拟暂停或超时，重启服务后由日志游标继续；同一 `event_id` 不重复推进。暂停只在当前 API 调用完成后的事件边界生效，向 C 返回“正在等待模型返回”。
4. 按场次设置最大玩家调用数、主持调用数、输出 token 上限、重试上限和费用预警阈值。额度由实际可用预算填写；先估算单局，再考虑批量运行。
5. 11 月 1 日功能冻结：不增加角色或玩法；只修正确性、稳定性、信息泄露和展示数据错误。规则或 Prompt 若改动，更新版本并保留旧对局版本标识。

规则断言通过率要按预设用例实算。不能用“某一方赢了”代替规则正确性，也不能把模型生成质量和规则正确率混为一个数字。
